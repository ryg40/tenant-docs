tenant-pi changes in one loop. A change starts as an issue. It ends as a merge commit on the branch `main`. A release then copies the reviewed files of `main` to the branch `portable`.

This page shows the whole loop on one diagram. The other Develop pages explain each part.

## The loop

Read the diagram from the top to the bottom. Each group with a title is one phase. The first line of each step names the role that does the step.

```mermaid
flowchart TD
    accTitle: The loop from an issue to a portable release
    accDescr: Six phases from the top to the bottom. Plan, build, review and merge repeat for each issue. The two release phases run when the owner wants a release. The last phase ends with the release entry.
    subgraph Plan["1. Plan"]
        direction LR
        a1["Owner<br/>decides the change"]
        a2["Coordinator<br/>writes one issue with<br/>its acceptance checks"]
        a1 --> a2
    end
    subgraph Build["2. Build"]
        direction LR
        b1["Worker<br/>creates the<br/>topic branch"]
        b2["Worker<br/>commits the change<br/>and its tests"]
        b3["Worker<br/>runs the four<br/>offline checks"]
        b1 --> b2 --> b3
    end
    subgraph Review["3. Review"]
        direction LR
        c1["Reviewer<br/>reads the branch and<br/>tests the behavior"]
        c2["Reviewer<br/>reports a verdict<br/>and the findings"]
        c3["Worker<br/>commits a fix<br/>for each finding"]
        c1 --> c2 --> c3
    end
    subgraph Merge["4. Merge"]
        direction LR
        d1["Coordinator<br/>merges the branch<br/>into main"]
        d2["Coordinator<br/>runs the checks<br/>on main"]
        d3["Coordinator<br/>records the results,<br/>closes the issue"]
        d1 --> d2 --> d3
    end
    subgraph Snapshot["5. Snapshot"]
        direction LR
        e1["Coordinator<br/>runs gates 1 to 5<br/>on main"]
        e2["Coordinator<br/>builds the snapshot with<br/>no push, and scans it"]
        e3["Worker<br/>runs the trial<br/>of gate 6"]
        e1 --> e2 --> e3
    end
    subgraph Publish["6. Publish"]
        direction LR
        f1{"Owner<br/>approves?"}
        f2["Coordinator<br/>pushes portable and<br/>the tag to GitHub"]
        f3["Coordinator<br/>writes the record, drafts<br/>the release notes"]
        f5["Owner<br/>approves the notes,<br/>creates the release entry"]
        f4["The snapshot<br/>stays local"]
        f1 -- yes --> f2 --> f3 --> f5
        f1 -- no --> f4
    end
    N(["Next issue:<br/>start again at 1"])
    Plan --> Build --> Review --> Merge
    Merge --> N
    Merge -- "the owner wants a release" --> Snapshot
    Snapshot --> Publish
```

Phases 1 to 4 repeat for each issue. Each merged issue changes `main`. Phases 5 and 6 run when the owner wants a release. A release changes `portable` and the mirror on GitHub.

When the review has no finding, the worker commits nothing more in phase 3. When the owner does not approve, the snapshot stays local.

## The roles

The loop has four roles. One role is a person. Three roles are agents. An agent is a program that works with a language model.

```mermaid
flowchart TD
    accTitle: The four roles and what each one gives to the next
    O["Owner, a person<br/>decides and approves"]
    C["Coordinator, an agent<br/>reports each result to the owner"]
    W1["Worker, an agent<br/>returns branch A<br/>and its check results"]
    W2["Worker, an agent<br/>returns branch B<br/>and its check results"]
    R["Reviewer, an agent<br/>returns the findings"]
    O -- "decisions and approvals" --> C
    C -- "issue A" --> W1
    C -- "issue B" --> W2
    C -- "one branch to review" --> R
```

| Role | Task | Limit |
| --- | --- | --- |
| Owner | Decides each change. Answers the open questions. Approves each release. The owner is the maintainer of the release. | Does not need to write code. |
| Coordinator | Splits the work into issues. Gives each issue to one worker. Merges the branches. Runs a release. | Does not push a release without the approval of the owner. |
| Worker | Takes one issue. Works on one topic branch. Reports the commands and the results. | Changes only the files of its issue. |
| Reviewer | Reads one branch. Tests the behavior. Reports the findings. | Makes no unrelated change. |

The method does not depend on agents. A person can take each agent role and run the same commands.

Workers can work at the same time, because each worker has its own issue and its own topic branch. A Git worktree gives each worker its own working tree of the same repository.

| 2 | Coordinator | Writes the issue. | An issue with the parts Why, Scope and Acceptance. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 3 | Worker | Creates the topic branch from `main`. | The branch `topic/i<number>-<short-name>`. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 4 | Worker | Commits the change and its tests. | Small commits. Each subject names the area and the issue. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 5 | Worker | Runs the four offline checks. | The last line of each check. | [Release gates](/tenant-pi/develop/gates/) |
| 6 | Reviewer | Reads the branch and tests the behavior. | A verdict and a list of findings. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 7 | Worker | Commits the fixes for the findings. | One more commit on the topic branch. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 8 | Coordinator | Merges the branch into `main` with `git merge --no-ff`. | A merge commit that names the branch and the issue. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 9 | Coordinator | Runs the checks on `main` and records them on the issue. | A closed issue with its evidence. | [From an issue to a merge](/tenant-pi/develop/issue-to-merge/) |
| 10 | Coordinator | Runs gates 1 to 5 on `main`. | The last line of each gate. | [Release gates](/tenant-pi/develop/gates/) |
| 11 | Coordinator | Builds the snapshot with `python3 scripts/publish_portable.py --no-push`. | A new commit and a new tag on the local branch `portable`. | [Portable release](/tenant-pi/develop/release/) |
| 12 | Coordinator | Scans the new snapshot commits at the level `fail`. | The result line of the scan, and the exit code 0. | [Portable release](/tenant-pi/develop/release/#the-scanner-level) |
| 13 | Worker | Runs the trial of gate 6 on a clean Linux user, from the snapshot. | Gate 6 recorded as passed, failed, blocked or not run. Gates 7 and 8 recorded as reports. | [Release gates](/tenant-pi/develop/gates/) |
| 14 | Owner | Approves the release. | An approval that the release issue records. | [Portable release](/tenant-pi/develop/release/) |
| 15 | Coordinator | Pushes with `python3 scripts/publish_portable.py`. | The branch and the tag on the mirror on GitHub. | [Portable release](/tenant-pi/develop/release/) |
| 16 | Coordinator | Writes the release record on the release issue. | The tag, each gate result and each open gap. | [Portable release](/tenant-pi/develop/release/) |
| 17 | Coordinator | Drafts the release notes after the last gate. | The notes: the kind of release, each gate result, the changes, each known defect and each open gap. | [Portable release](/tenant-pi/develop/release/#the-release-notes) |

## The rules of the loop

- One issue has one topic branch and one writer.
- An issue states its acceptance checks before the work starts.
- A worker claims an issue before the work starts.
- An issue with the label `needs-approval` waits for the approval of the owner.
- A check has one of four results: passed, failed, blocked or not run.
- Do not record a check as passed when it did not run.
- A merge uses `--no-ff`, so the history shows each topic branch.
- `main` stays in the development repository. Only the reviewed publish set goes to `portable`.
- The coordinator pushes a release only after the owner approves it.
- A release is a full qualification, or a fast track with gate 6 not run. The owner approves a fast track.
- The release notes are a release entry on the tag. The snapshot holds no notes file.
